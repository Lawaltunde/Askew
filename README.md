# Askew

A full-stack web application that generates 3 role-specific interview questions for a given job title using OpenAI via Spring AI.

**Live Demo:** _add your URL here after deployment_

---

## What This Does

Enter a job title (e.g. "Customer Success Manager"), click submit, and the app returns 3 thoughtful, role-specific interview questions generated by an LLM. Each generated interview is persisted to Postgres for history.

---

## Tech Stack

| Layer | Choice | Why |
|---|---|---|
| Backend | Spring Boot 3.x (Java 17) | Standard, well-supported, matches my skillset |
| Frontend | Vite + React | Minimal setup, fast dev server, simple production build |
| AI Integration | Spring AI + OpenAI | Clean `ChatClient` abstraction, easy provider swaps later |
| Model | `gpt-4o-mini` | Cheap enough that $5 of credit lasts a long time, fast, more than capable for this task |
| Database | Supabase Postgres | Real managed Postgres, generous free tier, standard JDBC URL |
| Backend Host | Render | Free tier, GitHub auto-deploy, supports Docker |
| Frontend Host | Vercel | Free, instant static deploys from GitHub |

### Why Spring AI

Spring AI gives a unified `ChatClient` API with auto-configuration. A single dependency and one config property gets you a working LLM client — no manual REST plumbing, no JSON parsing boilerplate. Swapping providers later (Anthropic, Gemini, Azure OpenAI) is mostly a config change.

### Why `gpt-4o-mini`

With $5 of OpenAI credit, `gpt-4o-mini` is the sweet spot — it's roughly 100× cheaper per token than `gpt-4o` and handles this task (generating 3 interview questions from a job title) easily. The credit will outlast the demo.

### Why Supabase

Real Postgres, real connection URL, no credit card needed for the free tier, and the dashboard makes inspecting the data trivial during a demo. The 500 MB database limit and 50K MAU ceiling are far beyond what this project needs.

## Architecture

```
┌─────────────────┐         ┌─────────────────────────┐
│  React (Vercel) │ ──POST─▶│  Spring Boot (Render)   │
│  Form + UI      │         │  /api/v1/interviews     │
└─────────────────┘         └───────────┬─────────────┘
                                        │
                       ┌────────────────┼────────────────┐
                       ▼                                 ▼
            ┌─────────────────────┐       ┌─────────────────────────┐
            │  Spring AI          │       │  Spring Data JPA        │
            │  ChatClient         │       │  → Supabase Postgres    │
            └──────────┬──────────┘       └─────────────────────────┘
                       │
                       ▼
            ┌─────────────────────┐
            │  OpenAI (gpt-4o-    │
            │  mini)              │
            └─────────────────────┘
```

### Layers (Backend)

- **Controller** — HTTP boundary, validates request, returns response
- **Service** — Orchestrates the AI call, parses the response, persists the result
- **AiService** — Thin wrapper around Spring AI's `ChatClient` (isolated for testability and prompt-tuning)
- **DTOs** — `InterviewRequest` (jobTitle) and `InterviewResponse` (jobTitle + List<String>)
- **Entity + Repository** — JPA persistence of generated interviews

> I intentionally skipped the DAO wrapper and the separate Mapper class. For a single endpoint, those add ceremony without value — Spring Data JPA already _is_ the DAO, and a few inline mapping lines beat a dedicated class.

## API

### `POST /api/v1/interviews/generate`

**Request**
```json
{
  "jobTitle": "Customer Success Manager"
}
```

**Response (200)**
```json
{
  "jobTitle": "Customer Success Manager",
  "questions": [
    "How would you identify and address churn risk in your first 90 days?",
    "Walk me through how you'd structure an onboarding program for a new enterprise client.",
    "Describe a time you turned around a struggling customer relationship."
  ]
}
```

**Errors**
- `400` — Missing or blank `jobTitle`
- `502` — OpenAI API failure or malformed response
- `500` — Unexpected server error

## Local Development

### Prerequisites

- Java 17+
- Node 18+
- An OpenAI API key from [platform.openai.com](https://platform.openai.com)
- A Supabase project (free) — grab the JDBC connection string from **Project Settings → Database → Connection string → JDBC**

### Backend

```bash
cd backend
export OPENAI_API_KEY=sk-...
export DATABASE_URL='jdbc:postgresql://db.<project>.supabase.co:5432/postgres'
export DATABASE_USERNAME=postgres
export DATABASE_PASSWORD=your_supabase_db_password
./mvnw spring-boot:run
```

Backend runs on `http://localhost:8080`.

### Frontend

```bash
cd frontend
npm install
echo "VITE_API_URL=http://localhost:8080" > .env.local
npm run dev
```

Frontend runs on `http://localhost:5173`.

## Database Schema

Hibernate auto-creates this from the `Interview` entity:

```sql
CREATE TABLE interviews (
    id BIGSERIAL PRIMARY KEY,
    job_title VARCHAR(255) NOT NULL,
    questions TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT NOW()
);
```

Questions are stored as a single delimited string (`||`-separated) to keep the schema flat. For a production app I'd use a child table or `jsonb`; for this demo it's intentionally simple.

## Deployment

### 1. Database → Supabase

1. Sign up at [supabase.com](https://supabase.com)
2. Create a new project — pick a region close to your Render region
3. Set a strong database password (you'll need it shortly)
4. Go to **Project Settings → Database → Connection string → JDBC** and copy the URL
5. **Connection pooling:** Supabase exposes a pooler on port 6543. Use the pooler URL for the backend, not the direct port-5432 URL — Render's free instances open and close connections often, and the pooler handles that gracefully.

### 2. Backend → Render

1. Push the `backend/` directory to a GitHub repo
2. On [render.com](https://render.com), create a new **Web Service**
3. Connect your repo, select the `backend` directory
4. Render will detect the `Dockerfile` and build automatically
5. Add environment variables:
   - `OPENAI_API_KEY`
   - `DATABASE_URL` (the Supabase pooler JDBC URL)
   - `DATABASE_USERNAME` (usually `postgres`)
   - `DATABASE_PASSWORD`
   - `FRONTEND_URL` (added after the next step)
6. Deploy

### 3. Frontend → Vercel

1. Push the `frontend/` directory to a GitHub repo (can be the same monorepo)
2. On [vercel.com](https://vercel.com), import the repo
3. Set the **Root Directory** to `frontend`
4. Add environment variable:
   - `VITE_API_URL` = your Render URL (e.g. `https://interview-gen.onrender.com`)
5. Deploy
6. Copy the Vercel URL back into Render's `FRONTEND_URL` env var so CORS works

## ⚠️ Free-Tier Cold Starts (Important)

There are **two** sleep behaviors on the free tier you need to know about:

1. **Render** spins down web services after 15 minutes of inactivity. First request after sleep takes 30–60 seconds.
2. **Supabase** pauses free-tier projects after 7 days of inactivity. Resuming takes ~30 seconds and is a one-click action in the dashboard.

**What this means for the demo:**
- Hit the live URL once before the reviewer visits to wake everything up.
- Mention this behavior in the README/submission notes so they don't think it's broken.
- If the reviewer visits cold, the first request will hang for up to a minute. Subsequent requests are fast.

**Mitigations I considered but rejected:**
- A cron pinger to keep Render warm — this is against Render's free-tier ToS and Supabase will still pause.
- Paying $7/month for Render's always-on tier — not in scope for a free-hosted demo.

For a real production deployment, paid tiers solve both problems.

## Security Notes

- The OpenAI API key lives **only** on the backend as an environment variable. It is never exposed to the browser.
- Database credentials live only on the backend as environment variables.
- CORS is restricted to the deployed frontend origin (not `*`).
- Supabase Row Level Security is irrelevant here because the Spring backend connects with the `postgres` service role over JDBC — we control access at the API layer.
- No personal data is sent in prompts — only the generic job title the user enters.
- Input is length-capped at 200 characters server-side to prevent prompt-injection abuse.

1. Create a Supabase project, save the JDBC pooler URL + password
2. Scaffold backend from [start.spring.io](https://start.spring.io) — pick **Spring Web**, **Spring Data JPA**, **PostgreSQL Driver**, **Validation**, **Lombok**

5. Add `InterviewController` → `InterviewService` → `AiService`, with JPA persistence
6. Add CORS config
7. Test locally end-to-end with `curl`
8. Scaffold frontend with `npm create vite@latest frontend -- --template react`
9. Build the form + loading/error UI
10. Test end-to-end locally
11. Write `Dockerfile`, push to GitHub
12. Deploy backend to Render with env vars, frontend to Vercel with env vars
13. Wire env vars in both directions, verify CORS works

## Known Limitations

- Free-tier cold starts on Render (~30–60s) and Supabase pause-after-7-days
- Questions stored as a delimited string instead of a child table — fine for a demo, not ideal for querying
- No rate limiting per IP — production would add `bucket4j` or similar
- Minimal input validation — production would add profanity filtering and stricter sanitization
- OpenAI free credit eventually runs out — for long-term hosting, swap in Gemini's actually-free tier (Spring AI makes this a config change)
